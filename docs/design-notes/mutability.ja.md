# `mut` と `imut`

English version: [mutability.md](mutability.md)

- 更新日: 2026-07-25

## 決定

既定のコレクションは**永続データ構造**です。更新すると新しい値が返り、元の値は変わりません。

```bash
clove -e '(def w [1 2 3]) (println (assoc w 0 99) w)'
# [99 2 3] [1 2 3]
```

破壊的更新が要る場合は `mut` で明示します。`mut` された値は別の型として表示され、
`assoc!` などで所定の位置を書き換えます。

```bash
clove -e '(def v (mut [1 2 3])) (println v) (assoc! v 0 99) (println v)'
# #<mut [1 2 3]>
# #<mut [99 2 3]>
```

## 理由

**既定は安全側に置く。** 永続データ構造は、共有された値が知らないうちに書き換わる事故を
構造的に防ぎます。Lisp 系の言語で期待される挙動でもあります。

**ただし速度が要る場所がある。** ゲームループのような毎フレーム更新する処理では、
更新のたびに新しいコレクションを作るコストが支配的になります。Clove が
[ネイティブビルド経路](two-phase-implementation.ja.md)を作った動機はまさに性能なので、
「速くしたいときに速くできる手段」は要ります。

**明示することで最適化の契約になる。** `mut` は単なる「速い版」ではなく、
**その値が他と共有されていないことを書き手が引き受ける**という宣言です。
この宣言があると、コンパイラは in-place 更新を安全に行えます。

つまり `mut` は3層で意味が違います。

| 層 | `mut` の意味 |
| --- | --- |
| インタプリタ | 破壊的更新を行う |
| 読み手 | この値は共有していない、という宣言 |
| ネイティブビルド | in-place 更新を要求する契約（設計として決定済み。後述） |

## 採らなかった案

**すべてを可変にする。** 性能は素直ですが、既定が危険側になります。共有された値が
どこで書き換わるか追えなくなるコストの方が大きいと判断しました。

**すべてを不変にする。** 実装は単純ですが、性能の逃げ道がなくなります。
ネイティブ経路を作った目的と合いません。

**末尾 `!` の有無だけで区別する。** `assoc` と `assoc!` を持つのは Clojure 的ですが、
それだけでは「この値は共有されていない」という情報が型に乗りません。
`mut` で値そのものを区別する形にしたのは、ネイティブビルド側が静的に判断できるように
するためです。

**`Imut<T>` 型を作る。** 不変側にも型を付ける案がありましたが外しました。
既定が不変なので、不変であることに名前を付ける必要がありません。
可変な方だけ `Mut<T>` で示します（[型ヒント](../language/type_hints.ja.md)）。

## ネイティブビルドでの扱い（未実装）

`mut` / `imut` をネイティブビルドの最適化契約として使う設計は決めてありますが、
**`clove build` にはまだ実装されていません**（2026-07-25 時点）。

```bash
clove build app.clv    # (mut [1 2 3]) を含むソース
# unsupported call in phase2 C build: mut
```

決めてある内容は次のとおりです。実装時の指針として残します。

- `mut` 文脈では in-place 更新を**必須**とし、共有があると証明できない場合は
  ビルドエラーにする（黙って新しい値を返すことはしない）
- `imut` 文脈では観測可能な意味で不変。共有がないと証明できる場合のみ内部的に
  in-place 最適化してよい
- 共有を断つ明示的な手段を用意する。新しいコンテナを確保して要素は浅くコピーする
  操作を持たせ、`vec` / `into` / `map` のような「新しい値は返すが共有がないことは
  保証しない」操作と区別する
- `mut` / `imut` の境界はネイティブビルドでは**実行時に切り替えられない**

現在のインタプリタには、共有を断つための専用の操作はありません
（`copy` は別用途の関数で、コレクションの複製ではありません）。

ネイティブ経路全体の対応範囲は
[インタプリタとネイティブビルドの2経路](two-phase-implementation.ja.md) と
[docs/phase2/](../phase2/README.md) を参照してください。
