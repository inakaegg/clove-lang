# マクロを持たない

English version: [no-macros.md](no-macros.md)

- 更新日: 2026-07-25

## 決定

Clove にマクロ機構はありません。`defmacro` も、syntax-quote (`` ` ``) も、
ユーザー定義の reader マクロもありません。

Lisp でマクロが担っていた役割は、次の2つに分けて固定しています。

- **special form** — 評価器が直接知っている構文。`defn` `let` `when` `cond` `->` など、
  Clojure ではマクロだったものも含めて言語側に持たせています
- **reader の糖衣** — `#(...)` `#{...}` `#/.../` `$rb{...}` など、リーダーに直書きされた記法

どちらもユーザーが増やすことはできません。構文の集合は処理系が固定します。

```clojure
(defmacro twice [x] (list 'do x x))
;; => Unbound symbol: 'defmacro'
```

## 理由

**静的解析が素直になる。** マクロがないと、読んだ AST と実行される AST がほぼ一致します。
Clove は LSP による補完・定義ジャンプ・型ヒント表示・診断を主要な機能として持っていて、
これらは「このフォームが何になるか」を展開せずに判断できることに強く依存しています。
マクロを許すと、LSP もフォーマッタも「ユーザーのマクロを展開しないと意味が分からない」
状態になります。

**フォーマッタが壊れない。** `clove fmt` はソースを読んで整形します。ユーザーが構文を
増やせる言語では、フォーマッタは知らない構文を安全に扱えません。

**メンタルモデルが1つで済む。** 「これは関数か、special form か、マクロか」を
読み手が判別する必要がなくなります。判別が要るのは関数と special form の2種類だけです。

**ネイティブビルドの前提を保てる。** [ネイティブビルド経路](two-phase-implementation.ja.md)は
ビルド時にコードの全体像が確定していることを前提にしています。実行時にコードを生成する
仕組みがあると、この前提が崩れます。

## 採らなかった案

**ユーザー定義の reader マクロ。** ファイルローカルに限定すれば安全ではないか、という案を
検討しましたが外しました。読み込み順の問題が残るうえ、LSP とフォーマッタが「このファイルの
reader 設定」をどう知るかという問題が解けません。処理系の外にあるツールが常に後追いになります。

**Clojure 互換のマクロ機構。** `defmacro` を入れれば Clojure のコードが動きやすくなりますが、
上記の利点をすべて失います。Clove は Clojure 互換を目標にしていません
（[Clojure から採らなかったもの](differences-from-clojure.ja.md)）。

**必要な構文を後からマクロで足せるようにする。** 「今は要らないが将来のために口だけ開けておく」
という案も外しました。口を開けた時点で LSP とフォーマッタは展開を考慮せざるを得ません。
構文が足りないと分かったら special form を足します。実際 `when-let` `cond->` `some->`
`doto` `with-open` などは、この方針で言語側に入れたものです。

## 影響

構文を増やしたいときは処理系を変更することになります。これは意図した制約です。
special form を追加する手順は [AGENTS.md](../../AGENTS.md) に書いてあります
（evaluator・compiler・型推論・docs・REPL 補完の5箇所を同時に更新する必要があります）。

`'quote` は残っています。データとしての S式を扱うためで、マクロのためではありません。

## 確認方法

```bash
clove -e '(defmacro f [x] x)'   # Unbound symbol: 'defmacro'
clove -e '(println `(1 2))'     # Unbound symbol: '`'
clove -e '(println #myTag{1})'  # Parse error: unknown reader tag: #myTag
clove -e "(println '(1 2))"     # => (1 2)
```
